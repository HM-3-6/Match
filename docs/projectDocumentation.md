## 1. 项目摘要

“赤途云迹”是一个以红色文化旅游为主题的 Web 平台。项目把分散的红色景点、历史故事、主题路线和购票入口整合到同一个页面体系内，试图解决“知道景点、却不知道怎么走；看过故事、却无法形成行程”的问题。

平台当前以**纯前端多页应用**的形式实现，共 15 个页面，覆盖：

- **精选旅游路线**：井冈山、延安、遵义、西柏坡 4 条主题路线；
- **路线地图**：基于高德地图的路线演示、节点打卡、范围限制与标记拖拽；
- **红色故事**：南昌起义、井冈山、于都、泸定桥、遵义会议、延安 6 组“新旧对比”内容；
- **红色景点购票**：3 张景点轮播与购票入口；
- **红色景点推荐**：5 个景点的星级推荐；
- **购票预约、后台、登录注册**：可演示的前端原型。

项目目前处于**前端原型阶段**：页面与主要交互可以完整走通，但数据仍以硬编码为主，尚未接入后端、真实账号、真实支付/票务与持久化存储。

## 2. 项目背景与意义

### 2.1 背景

红色旅游兼具文化教育、历史学习和旅行体验属性，近年来从“参观型”逐渐转向“研学型、体验型、路线型”。用户在出行前通常需要同时解决四件事：

1. 去哪里：有哪些红色景点、哪些路线值得走；
2. 看什么：景点背后的历史事件与精神内涵；
3. 怎么走：路线节点、地理位置、行程天数；
4. 怎么买票：开放时间、购票方式、预约与参观须知。

这些信息往往分散在攻略文章、地图应用、公众号和场馆购票系统中，用户需要在多个平台之间反复切换。

### 2.2 现有痛点

| 痛点             | 具体表现                                                   |
| :--------------- | :--------------------------------------------------------- |
| 内容碎片化       | 路线、故事、景点介绍彼此独立，缺少统一入口                 |
| 行程与内容脱节   | 看完故事后不知道如何组织成一条可执行的路线                 |
| 交互形式单一     | 以图文浏览为主，缺少地图、对比、轮播等参与感               |
| 服务链路不完整   | 从“了解”到“购票/预约”之间缺少顺畅的导流                   |
| 运营维护成本高   | 内容更新依赖改代码，缺少轻量后台                           |
| 移动端体验不足   | 地图演示页与部分页面尚未针对小屏做完整适配                 |

### 2.3 项目意义

- **文化传播**：用“路线 + 故事 + 地图”的组合，让红色文化从静态文字变成可感知的行程。
- **研学辅助**：为党支部、学校研学、家庭出行提供路线参考和内容预习材料。
- **服务导流**：把内容浏览、路线选择、地图确认与购票入口放在同一平台内，减少跨平台切换。
- **教学实践**：项目覆盖 HTML/CSS/JavaScript、地图 API、数据驱动渲染、响应式布局和前端工程规范，适合作为课程设计或团队实践项目。

### 2.4 品牌释义

“赤途云迹”由四个意象组成：

| 字 | 含义                                   |
| :- | :------------------------------------- |
| 赤 | 红色文化、红色基因                     |
| 途 | 旅游路线、行程与旅途                   |
| 云 | 线上平台、云端内容与服务               |
| 迹 | 足迹、打卡、寻访与记忆                 |

品牌口号：**红色文旅一站式平台**。

> 当前页面已将品牌名、页面主标题与页脚统一为“赤途云迹”；导航中的“云打卡”字样尚未同步，详见 7.5 节。

## 3. 项目目标与范围

### 3.1 总体目标

打造一个“看得见、走得进、留得住”的红色文旅入口：

- **看得见**：路线、景点、故事在一个页面内集中呈现；
- **走得进**：通过地图和行程节点，把内容转化为可执行的路线；
- **留得住**：通过新旧对比、路线地图、景点购票入口，延长用户停留与参与。

### 3.2 具体目标

| 编号 | 目标                       | 衡量方式                                                     |
| :--- | :------------------------- | :----------------------------------------------------------- |
| G1   | 建立统一的内容入口         | 首页可触达 4 条路线、6 个故事、5 个景点、购票与后台入口       |
| G2   | 让路线可视化               | 每条路线都有独立地图页，能显示节点、路线、打卡弹窗            |
| G3   | 强化红色故事表达           | 6 组新旧照片对比，支持拖动查看今昔变化                        |
| G4   | 打通“内容—购票”链路       | 首页可一键进入购票/预约页；路线页与详情页直达购票列入后续迭代 |
| G5   | 形成可演示的运营原型       | 后台具备看板、地点管理、打卡管理、调研、系统设置              |
| G6   | 保证多端基本可用           | 1440 / 1024 / 768 宽度下无严重布局错乱                        |

### 3.3 项目范围

**本期包含**

- 首页品牌区、栏目导航、路线、红色景点购票、景点推荐、红色故事；
- 4 个地图路线演示页；
- 6 个红色故事详情页；
- 红色景点购票/预约前端流程；
- 管理后台前端原型；
- 登录、注册前端流程；
- 静态资源、样式与基础交互。

**本期不包含**

- 真实支付、真实票务、订单状态、短信通知；
- 真实账号体系、权限系统、单点登录；
- 后端接口、数据库、文件上传；
- 实时客流、天气、交通等动态数据；
- 多语言、无障碍全量适配、SEO 深度优化；
- 小程序、App、微信生态接入。

## 4. 目标用户与使用场景

### 4.1 用户画像

| 用户类型         | 特征                                   | 核心诉求                                       |
| :--------------- | :------------------------------------- | :--------------------------------------------- |
| 研学组织者       | 党支部、学校、企事业单位带队人员       | 路线是否成体系、行程几天、能否购票、是否适合团队 |
| 自由行游客       | 对红色文化感兴趣的个人或家庭           | 景点是否值得去、怎么安排路线、开放时间与购票方式 |
| 学生 / 青年用户  | 视觉敏感、喜欢互动与分享               | 内容是否好看、有没有地图/对比/轮播等参与感     |
| 内容运营人员     | 负责景点、故事、路线和活动更新         | 能否低成本维护内容、查看数据、管理打卡记录     |
| 教师 / 讲解人员  | 需要素材用于课程、讲解或研学手册       | 故事是否准确、图片是否清晰、能否按主题检索     |

### 4.2 典型场景

**场景一：研学前规划**

> 组织者打开首页，查看 4 条主题路线，比较天数、适合人群和行程节点，进入地图页确认地理位置，再通过购票入口进入预约购票页填写信息。

**场景二：行前文化预习**

> 学生浏览红色故事区，拖动新旧照片对比，看到“石破天惊第一枪”“寻路遵义定乾坤”等卡片标题，进入详情页了解事件背景。

**场景三：景点购票**

> 用户在“红色景点购票”区浏览轮播图，点击“点击购票”，进入预约购票页选择景点、填写信息并看到成功弹窗。

**场景四：运营维护**

> 管理员进入后台，查看数据看板，维护地点与打卡记录，查看用户调研结果并调整内容。

## 7. 页面与体验设计

### 7.1 首页效果

![赤途云迹首页](./assets/homepage.jpg)

> 首页 1440px 宽度实际效果：品牌区 → 栏目导航 → 4 条路线卡片 → 红色景点购票 + 景点推荐 → 红色故事区。

### 7.2 布局说明

首页采用“**总—分**”结构：

1. **品牌区**：居中展示“赤途云迹”，下方是“红色文旅一站式平台”口号，底部一条细分隔线。
2. **栏目卡**：三栏等宽，分别锚定路线、云打卡/景点、景点推荐。
3. **路线区**：2×2 卡片网格。每张卡片包含主题徽章、路线名、简介、标签、节点时间轴、天数、适合人群和“查看详情”按钮。
4. **下半区**：左栏（约 1 份宽度）放“红色景点购票”和景点推荐；右栏（约 2 份宽度）放 3×2 的红色故事网格。
5. **页脚**：品牌名 + 口号。

这种布局的优点是首屏信息密度高、路线对比直观；缺点是左栏偏窄，购票轮播与景点列表的视觉权重不均衡。

### 7.3 视觉语言

| 维度     | 设计选择                                                                 |
| :------- | :----------------------------------------------------------------------- |
| 主色     | 中国红 / 砖红（`#b35927`、`#c0392b`、`#b71c1c`）                          |
| 背景     | 暖白、米色（`#fff`、`#f5efe9`、`#fffcf8`），避免纯白的冷感               |
| 卡片     | 8—20px 圆角、轻阴影、细边框，悬浮时上移                                    |
| 标题     | 首页品牌大字 + 栏目小标题；路线名 19px 加粗                               |
| 节点     | 红/橙圆点 + 虚线连接，首尾节点用实心与光晕区分                            |
| 故事     | 左旧右新，中间红色圆形滑块 + 白色分割线                                   |
| 地图     | 全屏地图 + 白色浮层面板 + 红色路线 + 红旗节点                             |
| 动效     | 卡片悬浮、路线节点高亮、图片对比拖动、轮播横向切换                        |

### 7.4 交互设计

- **路线卡片**：鼠标悬浮上移、阴影加深，点击“查看详情”在新标签打开地图页。
- **故事卡片**：拖动滑块实时裁剪右侧新照片；悬浮时底部浮出“拖动对比今昔”提示。
- **红色景点购票**：点击底部圆点切换 3 张景点图；点击“点击购票”打开预约购票页。
- **地图**：显示/隐藏路线、切换控件、限制范围、拖拽标记、点击红旗打卡。
- **后台**：侧边栏折叠、二级菜单展开、页面切换、表格增删改查、Toast 提示。

### 7.5 体验问题与改进方向

| 问题                                   | 影响                                             | 建议                                                   |
| :------------------------------------- | :----------------------------------------------- | :----------------------------------------------------- |
| 导航仍写“云打卡”，模块已改“红色景点购票” | 用户不知道点进去是购票还是打卡                   | 同步导航文案，或把“云打卡”拆成独立功能                 |

## 8. 技术方案概述

### 8.1 总体架构

```text
静态浏览器端
├── 页面层：15 个 HTML 页面
├── 样式层：src/static/css/*
├── 交互层：src/components/Javascript/*
├── 地图能力：maps.js（高德 JS API）+ mapReuse.js
├── 图表能力：chart.js（Chart.js）
└── 资源层：src/static/image/*
```

项目采用**多页应用（MPA）**，没有前端框架、构建工具和后端服务。页面之间通过普通链接跳转，数据通过页面内数组或对象渲染。

### 8.2 技术选型理由

| 选择             | 理由                                                       | 代价                                       |
| :--------------- | :--------------------------------------------------------- | :----------------------------------------- |
| 原生 HTML/CSS/JS | 零依赖、易部署、适合课程项目与静态托管                     | 复用与状态管理能力弱                       |
| 多页应用         | 每个页面职责清晰，便于分工                                 | 页面间共享状态困难，重复代码多             |
| 本地地图 SDK     | 不依赖外部脚本地址，演示稳定                               | 文件体积大，Key 暴露风险                   |
| 本地 Chart.js    | 后台图表开箱即用                                           | 仅用于演示，未接入真实数据                 |
| 无后端           | 原型阶段成本最低                                           | 无法真实注册、购票、打卡与持久化           |

### 8.3 运行与部署

```bash
# 在项目根目录启动静态服务
cd C:\Users\acy_1\Desktop\Match
python -m http.server 8000

# 访问
http://localhost:8000/src/index.html
```

部署时需注意：

- 站点根应为项目根目录，否则 `../src/static/...` 路径会 404；
- 高德地图需要配置 Key 的域名白名单；
- 纯静态托管即可（GitHub Pages、Nginx、对象存储等）；
- 若后续接入后端，需要改为同源代理或配置 CORS。

### 8.4 当前技术限制

- 所有业务数据写死在 JS/HTML 中，修改内容需要改代码；
- 没有统一数据层，页面之间无法共享用户、打卡、购票状态；
- 后台、购票、登录均为前端模拟，不能直接上线；
- 高德 Key 打包在 `maps.js` 中，存在泄露风险；
- 详情页样式内联，视觉规范难以统一维护；
- 缺少构建、Lint、自动化测试与错误监控。

## 11. 风险与应对

| 风险                       | 等级 | 影响                                       | 应对措施                                                     |

| 范围蔓延                   | 中   | 影响交付进度                               | 锁定 MVP，新需求进入下一迭代                                 |
| 后台无鉴权                 | 高   | 任何人可访问管理功能                       | 接入登录与角色权限，至少增加演示级口令                       |

## 13. 后续规划

| 版本 | 主题                     | 主要内容                                                               |
| :--- | :----------------------- | :--------------------------------------------------------------------- |
| v1.1 | 品牌与体验统一           | 统一“赤途云迹”品牌；修复导航“云打卡”与购票模块不一致；按钮配色；页面标题 |
| v1.2 | 购票体验完善             | 景点详情、票种/价格、日期与时段校验、订单状态、购票记录                 |
| v1.3 | 服务闭环                 | 后端接口、账号体系、真实支付/预约、短信/站内通知                       |
| v1.4 | 运营与数据               | 后台权限、内容审核、真实统计、调研分析、导出功能                       |
| v2.0 | 多端与生态               | 移动端 H5 / 小程序、地图导航、语音讲解、AR/VR 红色场景                 |

若后续恢复“云打卡/数字勋章”的产品定位，可在此基础上扩展：

- 打卡记录与定位校验；
- 勋章规则与进度；
- 打卡海报与社交分享；
- 与路线、景点、购票记录联动。

演进原则：

1. **先内容、后系统**：先把路线、故事、景点做扎实，再补账号与交易；
2. **先闭环、后扩展**：优先打通“路线—地图—购票”，再考虑社交与增值服务；
3. **先合规、后上线**：涉及身份证、手机号、位置等敏感信息时，必须先完成合规设计。
